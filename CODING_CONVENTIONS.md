# Соглашения по разработке ActiveBook

Этот документ предназначен **для разработчиков и ИИ-агентов**. Он описывает общие требования к написанию, чтению и организации исходного кода в репозиториях ActiveBook.

Соглашения о коде хранятся здесь, а не в `AGENTS.md`: последний описывает порядок работы ИИ-агентов и ссылается на эти правила. Специфичные технические ограничения репозитория могут дополнять общие соглашения. Если ESLint, Stylelint или TypeScript задают машинно проверяемые ограничения, они остаются нормативным источником для конкретного синтаксиса.

## Основная философия написания кода

Код пишется в первую очередь для человека, а не для компьютера.

Разработчик должен понимать происходящее при последовательном чтении сверху вниз,
не разбирая мысленно вложенные выражения и не удерживая в памяти промежуточные вычисления.

Предпочитайте:

- Последовательность действий вместо композиции выражений.
- Именованные смысловые условия вместо вложенных логических конструкций.
- Явное ветвление вместо неявного управления потоком выполнения.
- Разделение получения данных, их преобразования и использования.
- Простые решения вместо универсальных абстракций.
- Имена, объясняющие назначение значения, а не способ его получения.
- Увеличение количества строк, если это снижает когнитивную нагрузку.

Промежуточная переменная полезна, даже если используется только один раз,
когда её имя объясняет смысл вычисления.

Не заставляйте читателя самостоятельно выполнять декомпозицию выражения,
которую разработчик мог выполнить при написании кода.

При этом не применяйте эти принципы механически: декомпозиция должна упрощать
понимание, а не создавать дополнительный информационный шум.

Перед завершением работы самостоятельно перечитайте добавленный и изменённый код
с позиции человека, впервые знакомящегося с реализацией. Оцените не только
корректность, но и когнитивную нагрузку при чтении.

## Читаемость и структура

- Пишите код, понятный при последовательном чтении. Используйте имена по назначению,
  а не абстрактные `data`, `value`, `flag`, когда контекст этого не объясняет.
- Предпочитайте небольшие законченные операции, ранние выходы и разумную декомпозицию.
  Выносите повторяющуюся или сложную независимую логику; не создавайте классы,
  дополнительные уровни каталогов или обёртки ради формального единообразия.
- Разбивайте сложные выражения и вложенные структуры на осмысленные промежуточные
  значения. Не вводите временные значения только для их последующей перезаписи.
- Собственные функции должны принимать не более двух аргументов. При необходимости
  объединяйте параметры в объект. Сохраняйте стандартные сигнатуры API и колбэков.
- Не переименовывайте и не форматируйте несвязанный с задачей код.
- Для булевых значений используйте понятные `is`, `has`, `can`, `should`, `show`;
  обработчики событий обычно называйте `handle...`.

## Предпочтения по структуре кода

- Предпочитайте последовательный императивный код компактным выражениям, если это улучшает читаемость.
- Не используйте тернарные операторы в новом и рефакторируемом коде. Для ветвления используйте `if`, `else`, ранние выходы или другие понятные конструкции.
- Не объединяйте несколько самостоятельных действий в одну строку. Разделяйте получение данных, преобразование и использование результата, если это делает логику понятнее.
- Не создавайте длинные цепочки вызовов методов, когда промежуточные результаты имеют самостоятельный смысл.
- Не сокращайте количество строк в ущерб ясности. Минимальный объём кода не является самоцелью.
- При рефакторинге оценивайте не только корректность, но и удобство последовательного чтения кода человеком.

### Логические выражения и условия

- Не смешивайте вызовы функций и сложные логические операции в одном выражении.
  Получайте результаты функций заранее и сохраняйте их в осмысленно названных переменных.
- Если необходимость вызова функции зависит от другого условия, используйте отдельный блок
  `if`, а не вложенные логические выражения.
- Разделяйте сложные условия на самостоятельные смысловые проверки.
- Используйте положительные формулировки булевых переменных, чтобы уменьшить количество отрицаний.
- При рефакторинге сохраняйте ленивое вычисление там, где оно необходимо для корректности,
  предотвращения побочных эффектов или дорогостоящих операций.
- Не создавайте промежуточные переменные для тривиальных проверок, если это не улучшает читаемость.

**Неправильно:**

```ts
const isPlaybackActive = isSlideActive
  && (playback.initialized || (presented && canStart()));
```

**Правильно**, если `canStart()` — чистый предикат, который допустимо вычислять заранее:

```ts
const canStartPlayback = canStart();
const isReadyToStart = presented && canStartPlayback;
const canActivatePlayback = playback.initialized || isReadyToStart;
const isPlaybackActive = isSlideActive && canActivatePlayback;
```

Если вызов действительно должен зависеть от условия, используйте явное ветвление.
Например, когда функцию допустимо вызывать только после раскрытия страницы:

```ts
let canStartPlayback = false;

if (presented) {
  canStartPlayback = canStart();
}
```

Простые и очевидные проверки не требуют дополнительной декомпозиции:

```ts
if (!Number.isFinite(duration)) {
  return;
}
```

## TypeScript и ошибки

- Сохраняйте строгую типизацию. Сужайте `unknown` проверками; не используйте `any`,
  `as` и отключения диагностики для маскировки проблемы.
- Выделяйте содержательные вложенные структуры в именованные типы; не усложняйте
  тривиальные типы. Соблюдайте существующие места экспорта публичных контрактов.
- Проверяйте внешние данные, файловые операции и результаты дочерних процессов.
  Ошибка должна давать контекст операции и понятный ненулевой exit code в CLI.
- Не подавляйте исключения. Перехватывайте их там, где можно восстановиться или
  добавить полезный контекст; сохраняйте исходную причину.
- Не смешивайте разрешённость операции с отсутствием данных. Используйте явные
  условия и согласованные цепочки fallback для одного значения.
- Сохраняйте различия `null`, `undefined`, `false`, `0`, `''`, семантику `??` и `||`,
  короткое замыкание, ленивые вычисления и порядок побочных эффектов.

## Форматирование и импорты

- Применяйте локальные ESLint/Stylelint/EditorConfig. Не отключайте правила без
  обоснованной причины и не исправляйте массово существующие несвязанные ошибки.
- Новый код: 2 пробела, LF, финальная новая строка; JavaScript/TypeScript — одинарные
  кавычки, точки с запятой, запятые в многострочных конструкциях. Ориентир длины — 120.
- Для импортов TypeScript-типов всегда используйте отдельный `import type` и располагайте
  его перед импортами значений. Длинные импорты (свыше 100 символов) переносите.
- В объектах, деструктуризации, именованных импортах и экспортах допускается до двух
  элементов на одной строке. Три и более оформляйте многострочно, каждый на отдельной строке.
  Свойства spread и rest учитываются наравне с остальными элементами.
- Соседние JSX-элементы разделяйте пустой строкой, если хотя бы один из них многострочный.
  Однострочные JSX-элементы можно группировать без пустых строк.
- Массивы и деструктуризацию массивов с тремя и более элементами оформляйте многострочно:
  открывающую `[` и закрывающую `]` размещайте на отдельных строках, каждый элемент —
  на отдельной строке. Массивы из одного-двух элементов можно оставлять однострочными.
  Это относится и к массивам зависимостей React-хуков.
- В TypeScript-типах (объектных type literal, interface и mapped types) всегда переносите
  содержимое между `{` и `}` на отдельные строки, даже при одном-двух полях.
- Сложные условия разбивайте на строки или именованные проверки. Отделяйте итоговый return
  пустой строкой.
- Не применяйте стилистические правила механически в ущерб пониманию и корректности.

## React и JSX

### Общие принципы

Компоненты должны преимущественно отвечать за:

- Получение необходимых данных
- Подготовку данных для отображения
- Обработку пользовательских событий
- Рендеринг интерфейса

Сложную независимую логику выносить за пределы компонентов.

Не перегружать JSX вычислениями и преобразованиями данных.

**Respect API boundaries and React lifecycle.** Represent absence according to the receiving contract: domain data, controlled input, CSS, component or hook. Keep valid `null`/`undefined` inputs and controlled empty strings. Do not change mounting, state, hook order or side effects for cosmetic simplification; follow the Rules of Hooks and prevent numeric visibility guards from accidentally rendering zero.

### Вычисления перед JSX

Вычислять производные значения, подписи, описания и другую логику отображения перед `return`.

**Нежелательно:**

```tsx
<button>
  {isProjectBusy ? 'Подождите...' : 'Сохранить'}
</button>
```

**Предпочтительно:**

```tsx
let projectBusyStatusLabel = 'Сохранить';

if (isProjectBusy) {
  projectBusyStatusLabel = 'Подождите...';
}

return (
  <button>
    {projectBusyStatusLabel}
  </button>
);
```

Простые значения можно использовать непосредственно в JSX.

Не создавать промежуточные переменные для очевидных обращений к уже подготовленным данным.

### Деструктуризация перед JSX

Если в JSX используется больше двух свойств одного объекта, предпочитать предварительную деструктуризацию.

```tsx
components.map((componentCur) => {
  const {
    id,
    description,
    packageName,
    name,
    title,
  } = componentCur;

  return (
    <button
      key={id}
      type="button"
      title={description}
      onClick={() => onInsertCustomComponent(packageName, name)}
    >
      Добавить {title}
    </button>
  );
});
```

Если используется не больше двух свойств, деструктуризация необязательна.

Не выполнять избыточную деструктуризацию, если она ухудшает понимание кода.

### Обработчики событий

Объявлять многострочные или сложные обработчики отдельно перед JSX.

**Неправильно:**

```jsx
onDelete={(name) => {
  setProperty(name, undefined);
  commitStyle();
}}
```

**Правильно:**

```tsx
const handleDelete = (name: string) => {
  setProperty(name, undefined);
  commitStyle();
};

return (
  <Properties
    onDelete={handleDelete}
  />
);
```

Если обработчик уже имеет подходящую сигнатуру, передавать его напрямую.

```tsx
onDelete={handleDelete}
```

Не создавать промежуточную стрелочную функцию без необходимости.

Короткие однострочные обработчики допустимы, если они остаются понятными и не содержат сложной логики.

### Расположение обработчиков в пропсах

Пропсы обработчиков событий (`onClick`, `onChange`, `onFocus` и другие) размещать в конце списка.

Если обработчиков больше двух, отделять их от остальных пропсов пустой строкой.

Правило распространяется на:

- JSX-пропсы
- Деструктуризацию пропсов
- Типы и интерфейсы пропсов

```tsx
export const Images = ({
  images,
  canImport,

  onChange,
  onImportAsset,
  onDelete,
}: BackgroundImagesProps) => {
  // ...
};
```

### Форматирование JSX

Если элемент содержит `children`, открывающий тег, содержимое и закрывающий тег располагать на отдельных строках.

**Неправильно:**

```tsx
<span>Название эффекта</span>
```

**Правильно:**

```tsx
<span>
  Название эффекта
</span>
```

Исключения допустимы, если переносы могут нарушить пробелы или отображение смешанного текстового содержимого.

Соседние JSX-элементы предпочтительно отделять пустой строкой.

Это относится и к ситуациям, когда однострочный элемент соседствует с многострочным.

Не вставлять пустые строки механически, если элементы образуют единую тесно связанную конструкцию и разделение ухудшает читаемость.

### Условный рендеринг

Не использовать однострочные конструкции с `&&` для рендеринга компонентов.

**Нежелательно:**

```tsx
{showBackgrounds && <BackgroundInstances project={project} />}
```

**Правильно:**

```tsx
{showBackgrounds && (
  <BackgroundInstances project={project} />
)}
```

Сложные условия вычислять перед `return`.

Учитывать, что числовые и строковые значения в условиях React могут приводить к неожиданному отображению.

### Зависимости React-хуков

В массивах зависимостей сначала указывать значения данных, затем функции.

```ts
useEffect(() => {
  updatePreview();
}, [effectId, options, updatePreview]);
```

Не удалять необходимые зависимости ради устранения предупреждений ESLint.

Не изменять семантику эффектов при перестановке или рефакторинге зависимостей.

### Ref

Проект использует React 19.

- Не использовать `forwardRef` в новом коде
- Передавать `ref` как обычный prop
- При рефакторинге существующих компонентов использовать механизм React 19
- Проверять корректность типизации и передачи `ref`

## CSS и classnames

Для объединения и условного применения CSS-классов использовать исключительно библиотеку `classnames`.

Не использовать для формирования `className`:

- Тернарные операторы
- Конкатенацию строк
- Шаблонные литералы
- Массивы с `.join()`
- Самостоятельные функции объединения классов

**Неправильно:**

```tsx
className={colorDisabledReason ? styles.DisabledColors : styles.Colors}
```

```tsx
className={`${styles.Select} ${layoutStyles.Unit}`}
```

```ts
const classes = [styles.Button, variantClass, className]
  .filter(Boolean)
  .join(' ');
```

**Правильно:**

```ts
const editorScreenClassNames = classNames({
  [styles.EditorScreen]: true,
  [styles.isStructureVisible]: showStructure,
  [styles.isNarrativeHidden]: !showNarrative,
});
```

Одиночный статический класс передавать напрямую.

```tsx
className={styles.Button}
```

Не создавать промежуточные переменные для одиночного статического класса без необходимости.

## Организация исходников и тестов

### Общий принцип

Директории организуются по **принадлежности к сущности и области ответственности**, а не по формальному количеству уровней. Структуру усложняем постепенно, когда это улучшает навигацию.

- Один самостоятельный файл допускается оставлять рядом с файлом-владельцем. Не создавайте отдельную папку на каждый компонент или функцию без необходимости.
- Несколько самостоятельных файлов одного назначения группируйте внутри ближайшей логической области. Для утилит и хуков действуют отдельные правила ниже.
- Если одной сущности нужны несколько исходных файлов (например, React-компонент и его SCSS Module), выделяйте для неё собственный каталог.
- Подкомпонент с единственным файлом может оставаться рядом с родителем, например `PageWrapper/Header.tsx`. Если подкомпонентов становится несколько, размещайте их в `PageWrapper/components/`.
- Если подкомпонент разрастается, выделяйте `components/Header/` с собственными файлами. **Правила применяются рекурсивно** к вложенным компонентам и подсистемам.
- Не дробите небольшую логику на множество файлов ради соблюдения шаблона. Не проводите массовые перемещения в задачах, не связанных со структурой.

### Утилиты и хуки

- Одну или несколько утилит размещайте в `utils.ts`, а один или несколько React-хуков — в `hooks.ts`, если все соответствующие функции помещаются в файл без нарушения действующего ограничения ESLint `max-lines`.
- Если утилиты или хуки не помещаются в соответствующий общий файл по `max-lines`, создавайте соответственно `utils/` или `hooks/` и разделяйте код на несколько осмысленно названных файлов. В каждом каталоге создавайте `index.ts` для удобного импорта.
- Для **одной** утилиты или **одного** хука всегда допустимо сразу создать отдельный каталог `utils/` или `hooks/` с файлом внутри, даже если ограничение `max-lines` не достигнуто. В таком случае также используйте `index.ts` как точку экспорта.
- Ориентируйтесь на эффективное значение `max-lines` из ESLint-конфигурации соответствующего репозитория, а не на произвольное фиксированное число строк. Разбиение по файлам не отменяет ограничение `max-lines` для каждого из них.
- Применяйте эти правила на ближайшем логическом уровне; не переносите утилиты и хуки в общие каталоги без необходимости.

### Тесты

- Если исходник сопровождает **один** тестовый файл, тест можно оставить рядом: `utils.ts` и `utils.test.ts`. Само наличие этого теста **не требует** создания `utils/`.
- Если в одной логической области **два и более** тестовых файла, выделяйте `tests/` рядом с владельцем. Это относится и к смеси unit, component и browser тестов.
- Тест, у которого нет очевидного соседнего исходника/владельца (интеграционный или сквозной сценарий), кладите в `tests/` ближайшего подходящего уровня, а не в `components/` только ради размещения.
- Самостоятельные интеграционные и браузерные сценарии уровня приложения размещайте в корневом `tests/`, группируя их по предметной области.
- Тестовые фикстуры, моки и вспомогательные файлы размещайте рядом с обслуживаемыми тестами либо в общем каталоге тестовой инфраструктуры внутри `tests/`.
- В `scripts/` запрещено размещать тестовые файлы, тестовые сценарии и тестовые фикстуры. Этот каталог содержит только инструментальные скрипты, включая раннеры, которые запускают тесты из `tests/`.
- Если в `tests/` собираются тесты нескольких сущностей, группируйте их **по сущности**: `tests/Header/`, `tests/HeaderLeft/`, `tests/HeaderRight/`. Например, для каждого Header могут находиться рядом один browser- и один component-тест.
- Если тестов одного вида **для одной сущности** становится много, можно добавить вложенный `browser/`, `component/` или `unit/` внутри `tests/<Сущность>/`. Не создавайте эти каталоги заранее и не группируйте сначала по типу теста, если это разрывает тесты одной фичи.
- Используйте имена, распознаваемые тестовым раннером: `*.test.ts`, `*.browser.test.tsx`, `*.component.test.tsx` и существующие конфигурации. Суффикс `component` — в единственном числе.
- Для каталогов тестов используйте обычное имя `tests/`. `__tests__/` не требуется, если проект явно не придерживается такого соглашения.
- По мере появления новых файлов реорганизуйте только относящуюся к текущей задаче область.
- Подключайте инфраструктурные проверки к штатным npm-командам проекта. В общем наборе проверок один и тот же тест не должен повторно запускаться через несколько команд; отдельные команды для ручного запуска поднабора допустимы.

Пример для нескольких подкомпонентов и тестов:

```text
PageWrapper/
├── PageWrapper.tsx
├── PageWrapper.module.scss
├── components/
│   ├── Header/
│   │   ├── Header.tsx
│   │   ├── Header.module.scss
│   │   └── index.ts
│   ├── Footer.tsx
│   └── index.ts
└── tests/
    ├── Header/
    │   ├── Header.browser.test.tsx
    │   └── Header.component.test.tsx
    └── Footer.component.test.tsx
```

### Экспорты и внутренние зависимости

- В каталоге с несколькими экспортируемыми TS/JS-модулями, которые составляют единый публичный API, используйте `index.ts`. Например, `import { Header, Footer } from './components';`.
- Для отдельного каталога компонента допускается `Header/index.ts`, если он улучшает публичный импорт. Не создавайте его автоматически ради единообразия, когда публичного API нет.
- Внутри одной директории импортируйте соседние модули напрямую, если импорт через её же `index.ts` создаёт циклическую зависимость.
- Для `tests/`, `styles/`, `assets/` и других каталогов, не экспортирующих TS/JS API, `index.ts` не нужен.
- Вспомогательную логику без зависимости от React оформляйте как утилиты, повторно используемую логику React — как хуки. Размещение определяйте по разделу «Утилиты и хуки».
- Эти рекомендации относятся не только к компонентам, но и к любым другим группам файлов.

## Тексты пользовательского интерфейса

Эти правила относятся к текстам, которые видит пользователь ActiveBook.

### Обращение к пользователю

Использовать вежливое обращение на «Вы».

Не переходить на «ты» в интерфейсных сообщениях.

### Пунктуация

Не ставить точку в конце последнего или единственного предложения интерфейсного текста.

**Нежелательно:**

```ts
const message = 'Проект успешно сохранён.';
```

**Правильно:**

```ts
const message = 'Проект успешно сохранён';
```

Если текст состоит из нескольких предложений, сохранять необходимые знаки препинания между ними.

Вопросительные, восклицательные знаки и другие смысловые знаки пунктуации сохранять.

### Кавычки

В русскоязычных текстах интерфейса использовать кавычки-лапки `"..."`, а не кавычки-ёлочки `«...»`.

Правило не относится к синтаксису строк TypeScript, JSON и другим техническим конструкциям.

### Область применения

Правила интерфейсной пунктуации и обращения не распространяются автоматически на:

- Документацию
- Комментарии в коде
- Технические сообщения консоли
- Тексты исключений
- Внешние данные

В этих случаях использовать оформление, соответствующее контексту.

## Корректность изменений и проверки

- Рефакторинг должен сохранять поведение, публичные контракты, порядок асинхронных операций и необходимые проверки отсутствующих значений.
- Перед изменением установите исходную семантику и проверьте места использования. При сомнениях подтвердите безопасность тестами или сохраните реализацию.
- Покрывайте нетривиальную логику и исправления ошибок тестами, включая отрицательные сценарии.
- Используйте стандартные API, когда их достаточно. Каждая новая зависимость должна решать реальную задачу.
- Не форматируйте и не перемещайте несвязанный код только ради соблюдения новых соглашений.
